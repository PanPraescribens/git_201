## Exercice 01

### 1. Créez un répertoire de travail et allez dedans
```bash
mkdir 01_01
cd 01_01
```

> 💡 Via `td go 1` ? Vous y êtes déjà, passez directement à l'étape 2.
> En cas de doute sur votre position, `td check` vous dira où vous êtes —
> il détecte même le piège du dossier-dans-le-dossier.

### 2. Créez votre repo
```bash
git init
```

### 3. Commencez à créer des fichiers
```bash
touch main.txt                          # crée un fichier vide
echo 'MonMotDePasse!' > secrets.txt     # crée un fichier avec un peu de texte
```

> 💡 Vous verrez peut-être : `warning: LF will be replaced by CRLF…`.
> Pas de panique : c'est votre Windows qui vous dit qu'il convertira les fins
> de ligne au prochain passage de git. C'est sans danger — et c'est exactement
> le sujet de la leçon 1 (fins de ligne, `.gitattributes`…). Si ça vous agace :
> `git config --global core.autocrlf input`.

NB : au passage, `A_FAIRE.md` (votre liste de tâches, si vous êtes passé par
`td go 1`) est parti dans l'index avec le reste. On le garde pour l'instant —
il va nous servir d'exemple à l'exercice 2, quand nous verrons `.gitignore`. 😉
(Pas de `A_FAIRE.md` ? Créez un fichier texte quelconque : il jouera le même rôle.)

### 4. Ajoutez tout à l'index git
```bash
git add .
```

### 5. Vous avez été un peu vite ; enlevez le fichier secrets.txt avant de faire un commit !
```bash
git rm --cached secrets.txt
```

NB : il existe d'autres commandes pour retirer un fichier de l'index
(`git restore --staged`, `git reset HEAD <fichier>`)… mais elles échouent ici !
Regardez le message d'erreur : `HEAD` n'existe pas encore, car **HEAD est né
avec votre premier commit**. Ce n'est pas un bug, c'est un apprentissage. 😉

### 6. Faites un commit
```bash
git commit -m "Ajoute main.txt"
```

Maintenant que HEAD existe, on va pouvoir s'en servir.

Ré-ajoutez le fichier secrets.txt, puis recommencez le retrait —
cette fois, les autres commandes fonctionnent (voir 6<sup>bis</sup>) !

### 6<sup>bis</sup>. Rajoutez le fichier et enlevez-le de l'index à nouveau
```bash
git add secrets.txt
git restore --staged secrets.txt
# ou encore
git add secrets.txt
git reset HEAD secrets.txt
```

NB : cette fois les deux fonctionnent, puisqu'il y a un commit. Constatez avec
`git status` que `secrets.txt` est bien de retour en "non suivi", et que rien
dans votre répertoire n'a été effacé.

### 7. Marquez l'exercice comme terminé
```bash
git tag ex01
```

Un marqueur de fin d'exercice — et un point de retour pratique :
`git checkout ex01` ou `git reset --hard ex01` vous ramène ici à tout moment.

## Exercice 02

### 1. Un repo prêt à l'emploi

Rien à taper : `td go 2` a créé le dossier **et préparé le repo dans l'état
de fin de l'exercice 1** — `main.txt` et `A_FAIRE.md` commités. Vérifiez avec
`git log` et `ls` si le cœur vous en dit : c'est ce repo qui va nous servir.

### 2. Protégeons-nous : créons un `.gitignore`
```bash
echo '/secrets/**' >> .gitignore
echo 'A_FAIRE.md'  >> .gitignore
```

Le `.gitignore` est un fichier texte à la racine du dépôt, qui liste les
motifs (patterns) des fichiers que git doit **ignorer** — ni les afficher
comme non suivis, ni les ajouter avec `git add .`.
La syntaxe se travaille à l'instinct, et vous l'aurez en TD jusqu'à ce
qu'elle devienne réflexe !

### 3. Testons tout de suite
```bash
mkdir secrets
echo 'MonSecret' >> secrets/secrets.txt
git status
```

Rien à signaler : `secrets/` est invisible pour git. Vous pouvez y créer ce
que vous voulez, aucun `git add .` ne le surprendra jamais.

### 4. Le piège : A_FAIRE.md refuse de disparaître !
```bash
git status
```

`A_FAIRE.md` apparaît toujours ? Normal : il a été **commité** à l'exercice 1,
donc il est **déjà suivi** — et le `.gitignore` ne s'applique qu'aux fichiers
que git ne connaît pas encore. Pour un fichier déjà suivi, il faut en plus le
retirer de l'index, sans effacer le fichier :
```bash
git rm --cached A_FAIRE.md
```

### 5. Commit final
```bash
git add .          # .gitignore + la désindexation de A_FAIRE.md
git commit -m "Ajoute .gitignore"
git tag ex02       # crée un tag, qui permet de référencer un commit facilement
```

## Exercice 03

### 1. Un repo dans l'état de fin de l'exercice 2

`td go 3` a préparé le repo : `main.txt` et `.gitignore` commités, le dossier
`secrets/` à l'abri. (Constatez au passage que la fin de l'exercice 2, c'est
un repo tout ce qu'il y a de plus ordinaire — le travail de protection est
invisible, et c'est bien le but !)

### 2. Éditons main.txt… et commettons une vraie erreur
```bash
echo 'Hello world!' >> main.txt      # ajoute du texte sans écraser
echo 'mot_de_passe=supersecret' > config_local.txt
git add .
git commit -m "Ajoute hello dans main"
```

Oh non ! Notre `.gitignore` protège `secrets/`, mais ce nouveau fichier
`config_local.txt` était au premier niveau : il est parti dans le commit !

### 3. Enlevons-le de notre dépôt
```bash
git rm config_local.txt
git commit --amend
```

Le `commit --amend` a écrasé notre commit précédent. Mais maintenant on a
perdu `config_local.txt` entièrement !

### 4. Revenons en arrière

> ⚠️ **Ce `reset --hard` est volontairement destructeur** : c'est le sujet de
> cet exercice. Il supprime le commit *et* les modifications non validées du
> répertoire de travail. C'est justement ce que nous allons réparer juste
> après — ne le faites pas sur un vrai projet ! 😄

```bash
git reset --hard HEAD~1   # revient au commit parent "Ajoute main.txt"
```

Problème : on a certes fait disparaître notre erreur, mais on a également fait
disparaître nos modifications dans main.txt !
```bash
cat main.txt
```
On voit que le fichier est vide.

Comment le récupérer ? On sait qu'il existait avec les modifications dans le
dernier commit maintenant disparu.

### 5. Récupérons le fichier main.txt modifié
```bash
git reflog
# va nous montrer le commit "Ajoute hello dans main"
# notez bien la référence au commit — prenez la ligne la plus récente (celle d'en haut).
# qui est du style HEAD@{n} — encore une notation alternative pour naviguer dans le reflog !

git checkout hash-du-commit-Ajoute-hello -- main.txt
# ATTENTION aux espaces autour du --
```

Normalement vous avez à ce stade récupéré la version main.txt avec "Hello world" dedans.

Vérifiez que le fichier est bien indexé avec `git status` sinon ajoutez-le.

Vous n'avez plus `config_local.txt` dans le répertoire.

### 6. Réparons durablement : le .gitignore prend le relais
```bash
echo 'config_local.txt' >> .gitignore
git add .gitignore
git commit -m "Ignore config_local.txt"
git tag ex03
```

Recréez `config_local.txt` autant que vous voulez : cette fois, git regarde
ailleurs. C'est tout l'intérêt de l'exercice 2 — le travail d'avant paie !

## Exercice 04

### 1. Un repo tout neuf
```bash
cd ..
mkdir 01_04 && cd 01_04
git init
```

(Via `td go 4` ? Vous y êtes déjà — seul `git init` est nécessaire.)

### 2. Créons un poème, et mettons-le dans l'index
```bash
echo 'Il était une fois'  > poeme.txt
echo 'un petit repo'     >> poeme.txt
git add poeme.txt
```

### 3. Modifions le fichier SANS re-stager
```bash
echo 'la fin' >> poeme.txt
```

### 4. Regardons git status : qu'est-ce que c'est que ça ?
```bash
git status
```

`poeme.txt` apparaît **deux fois** : une fois "staged" (dans l'index, la
version à 2 lignes), une fois "modified" (sur le disque, la version à
3 lignes). Les deux versions coexistent !

### 5. Voyons les deux versions
```bash
git diff            # disque vs index : la ligne "la fin" n'est PAS dans l'index
git diff --cached   # index vs dernier commit : les 2 lignes ajoutées, pas la 3e
```

### 6. Commettons… et regardons ce qui est parti dans le commit
```bash
git commit -m "Ajoute le poème"
cat poeme.txt               # 3 lignes
git show HEAD:poeme.txt     # 2 lignes !
```

Le commit a pris la version de **l'index** — celle du moment du `git add` —
pas celle de votre éditeur. Git ne devine pas : il fait précisément ce
qu'on lui dit !

### 7. Réparons avec --amend
```bash
git add poeme.txt
git commit --amend
git show HEAD:poeme.txt     # 3 lignes : cette fois c'est bon
git tag ex04
```

## Exercice 05 (bonus)

Pour les try-hardeurs 😄 : le drill des trois resets. Même point de départ à
chaque fois, trois comportements radicalement différents.

### 1. Un repo neuf avec trois commits
```bash
cd ..
mkdir 01_05 && cd 01_05
git init

echo 'ligne 1' > compteur.txt
git add compteur.txt && git commit -m "ligne 1"

echo 'ligne 2' >> compteur.txt
git add compteur.txt && git commit -m "ligne 2"

echo 'ligne 3' >> compteur.txt
git add compteur.txt && git commit -m "ligne 3"
```

### 2. --soft : le retour le plus doux
```bash
git reset --soft HEAD~1
git status
```
Le commit a disparu, mais tout est **re-stagé** : index et répertoire intacts.
On peut re-committer tel quel, ou re-stager autrement.

### 3. --mixed (le défaut) : on garde le disque
```bash
git commit -m "ligne 3"
git reset HEAD~1            # --mixed est le défaut
git status
```
Le commit a disparu, les modifications sont **dans le répertoire mais plus
dans l'index** : il faudra re-faire `git add`.

### 4. --hard : on ne garde rien
```bash
git add compteur.txt && git commit -m "ligne 3"
git reset --hard HEAD~1
git status && cat compteur.txt
```
Le commit, l'index, ET les modifications du répertoire : tout a disparu.

> ⚠️ Et s'il y avait des modifs non commitées dans d'autres fichiers ? Elles
> seraient parties aussi. `--hard` ne discute pas.

### 5. Le sauvetage
```bash
git reflog
git reset --hard hash-du-commit-ligne-3
cat compteur.txt    # les 3 lignes sont de retour
git tag ex05
```

Moralité :

| option | commit | index | répertoire |
|---|---|---|---|
| `--soft` | ✗ | ✓ | ✓ |
| `--mixed` (défaut) | ✗ | ✗ | ✓ |
| `--hard` | ✗ | ✗ | ✗ |
